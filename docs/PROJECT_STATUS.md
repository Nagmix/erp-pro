## الملخص التنفيذي

ERP-Pro نظام ERP عربي (RTL) مبني على **Next.js 16 + ERPNext v16 + HRMS**، منشور على
BunnyShell (`erp-pro-full` — https://app-odxvfq.bunnyenv.com/) ويعمل فعلياً بشركة مهيأة
(شركة الاختبار / YER / اليمن / سنة مالية 2026 / 96 حساباً).

النظام **يغطي نطاقاً وظيفياً واسعاً** (~92% من الصفحات متصلة بـ ERPNext فعلياً) وأُغلقت فيه
حملة الأمان الكاملة (14 ثغرة حرجة P0 + 12 متوسطة P1). ما تبقى من عناصر P3 وP2 موثق أدناه
بشفافية.

## البنية التحتية (بعد P3)

- Docker: `node:22-alpine` + `npm ci` + بلا `.env` داخل الأرتيفاكت.
- CI: `prisma validate` + `tsc` + `lint` + `vitest` + **`next build` كامل** + `npm audit`.
- Redis ×3 بكلمة سر إلزامية (`REDIS_PASSWORD`)؛ MariaDB داخلي فقط بلا منفذ منشور.
- docker-compose بلا كلمات سر افتراضية، مع healthchecks وحدود ذاكرة.
- bns-init.sh يفشل صراحة عند فشل new-site/migrate/HRMS (لا بدء نظام مكسور بصمت).
- نسخ احتياطي ليلي `bench backup --with-files` (استبقاء 7).
- قفل حزم واحد: `package-lock.json` مع `packageManager: npm@10.9.0` (bun.lock حُذف).

### دين تقني معلوم (INF-14 — توقف مقصود)

مخازن SQLite المحلية (إقرارات ضريبية، استقطاع، صلاحيات خزائن، سجل تدقيق، نسخة بوابة
المطور) ما زالت قائمة. **تم تخفيف أخطر جزء**: دمج «الأحدث يفوز» الثنائي JSON↔SQLite في
بوابة المطور أُلغي — ملف JSON صار المصدر الموثوق والوحيد وSQLite نسخة استعادة أحادية
الاتجاه. الترحيل الكامل إلى Frappe DocTypes يتطلب هجرة بيانات حية واختباراً على بيئة
متصلة — أُجل كدين تقني موثق (وليس جزءاً من P2 المؤجلة تجارياً).

### دين تقني معلوم (QUA-02 — توقف مقصود)

تكرار ~850 سطراً بين `sales/pos` و`pos/sell` قائم — دمج شاشتي POS في مكوّن واحد
عملية إعادة هيكلة كبيرة تتطلب اختبار انحدار شامل لشاشة البيع الحرجة، وأُجلت لجلسة
مخصصة بعد استقرار هذا الإصدار.
